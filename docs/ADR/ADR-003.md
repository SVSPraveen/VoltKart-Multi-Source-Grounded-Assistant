# ADR-003: Document Retrieval Pipeline & Version Resolution

## Status
Accepted

## Context
Enterprise document bundles often contain multiple revisions of policies where newer versions omit legacy rules rather than amending them. Naive "filter to newest document" retrieval fails on questions where only an older version stated the fact.

## Decision
1. **Hybrid Retrieval:** Standard library SQLite FTS5 (BM25) fused with local dense embeddings (`all-MiniLM-L6-v2` via `fastembed` ONNX) using Reciprocal Rank Fusion (RRF).
2. **Sibling Expansion:** For any matched section chunk, retrieve corresponding section chunks across all versions within the same document family.
3. **Deterministic Claim-Level Resolution:** Execute structured extraction per version, verify verbatim evidence quotes as exact normalized substrings of source chunks, and select the latest document date in code among versions stating the fact. Disclose fallback if an older version is used.

## Alternatives Rejected
1. **External Vector Databases (Pinecone, Chroma, Qdrant):** Introduce external service dependencies, network overhead, and installation friction for a small-to-medium corpus.
2. **Dense-Only Retrieval:** Performs poorly on exact alphanumeric codes (`O00174`, `S04`) and specific section headings.

## Executive Trade-off Analysis
- **User Value:** Zero external API latency/costs for retrieval, robust multi-version provenance, completely reproducible offline.
- **Risk:** CPU embedding time; mitigated by small corpus size (< 100 chunks).
- **Cost to Reverse:** Low.
